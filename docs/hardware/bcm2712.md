# BCM2712 / Raspberry Pi 5 hardware reference

Working notes for the model. Facts are taken from the sources listed at the
end; anything marked **unverified** is a best guess that a work unit in
[PLAN.md](../PLAN.md) must confirm on real hardware.

## Processor complex

| Item | Value | Notes |
| --- | --- | --- |
| Cores | 4 × Cortex-A76, one cluster | MIDR `0x414fd0b1` (r4p1) on C1 silicon |
| MPIDR | `Aff1` = core, `Aff0` = 0 | device-tree `reg` = `0x000..0x300`; the A76 also sets `MT` (bit 24), which the SoC's `mpidr-mt` CPU property does |
| Caches | 64 KiB L1I/L1D, 512 KiB L2 per core, 2 MiB shared L3 | QEMU's `cortex-a76` has no L3 in `CLIDR`/`CCSIDR` |
| Generic timer | 54 MHz (crystal) | `CNTFRQ_EL0 = 54000000` |
| Physical address size | 40 bits | peripherals above `0x10_0000_0000`, MSI doorbell at `0xff_ffff_f000` |
| Interrupt controller | GIC-400 (GICv2 + Security + Virtualization Extensions) | 32 priority levels; 288 SPIs assumed (**unverified**) |
| PMU interrupt | SPI 16 + core, level-high | from the `arm-pmu` node in the Raspberry Pi firmware's `bcm2712-rpi-5-b.dtb`; upstream `bcm2712.dtsi` has none (**unverified** on hardware) |

## Physical memory map

DRAM is contiguous from 0 (1, 2, 4, 8 or 16 GiB). The device tree's `soc`
bus maps bus address `0x0` to CPU address `0x10_0000_0000`; `bcm2712.dtsi`
unit addresses are therefore offsets from there.

The table is C1 silicon's, as on the 4 and 8 GiB launch boards. D0
silicon, on later boards, has smaller pin controllers with another
layout (`brcm,bcm2712d0-pinctrl`, `0x20`, and `-aon-pinctrl`, `0x1c`)
and raises UART10 on SPI 120; WS9.8 in [PLAN.md](../PLAN.md) lists every
difference found so far.

The addresses, sizes and names of the blocks are not copied here: the
model's `bcm2712_memmap[]` in
[`overlay/hw/arm/bcm2712.c`](../../overlay/hw/arm/bcm2712.c) is their one
source, and the SPI each raises is the `BCM2712_SPI_*` enum in
[`overlay/include/hw/arm/bcm2712.h`](../../overlay/include/hw/arm/bcm2712.h).
Both follow Linux's `bcm2712.dtsi` (and the firmware's tree where it has
blocks the upstream one lacks), which the built-in device tree, generated
from them, is validated against (`make check-dt`). Which QEMU model
serves each block, and with what, is in [the machine
documentation](../../overlay/docs/system/arm/raspi5b.rst); a block with
no model is an `unimplemented-device` named after its `bcm2712_memmap[]`
entry, which `-d unimp` logs.

Everything else between `0x10_0000_0000` and `0x10_7fff_ffff` is covered by
two catch-all windows, `bcm2712.axi` and `bcm2712.soc`. The downstream
Raspberry Pi device tree adds blocks not listed above, notably a 40-bit DMA
controller (`0x10_0001_0000`) and IOMMUs (`0x10_0000_5100`,
`0x10_0000_5200`, cache at `0x10_0000_5b00`); its AVS monitor/thermal
sensor (`0x10_7d54_2000`) is modelled (**bcm2711-avs-monitor**, the
temperature register).

MIP SPI numbers follow the Linux `irq-bcm2712-mip` driver: an MSI with data
value `n` raises SPI `msi-base + n`, and `brcm,msi-offset` is the first data
value a controller hands out. MIP0 therefore owns data 0–63 on SPIs
128–191 and MIP1 data 8–15 on SPIs 255–262 (its `msi-ranges` base of 247
plus the offset); SPI 247 itself belongs to `interrupt-controller@7d517000`.

### PCIe windows

Each root complex's outbound window is its `BCM2712_PCIE*_MEM` entry of
`bcm2712_memmap[]`: 64-bit prefetchable PCI memory (PCI `0x4_0000_0000`)
from its start, and a 32-bit window above that. Inbound, all three map PCI
`0x10_0000_0000` to DRAM at 0 (64 GiB), and PCIe1 and PCIe2 map the MSI
address (`BCM2712_MIP_MSI_ADDR`) to their MIP's registers.
`bcm2712_fdt_pcie()` writes the `ranges` and `dma-ranges` the guest gets
from these.

## RP1 south bridge

PCI `1de4:0001` behind PCIe2. BAR1 (4 MiB) exposes the peripheral bus at RP1
address `0x4000_0000`; interrupts are delivered as 61 MSI-X vectors
configured through `MSIX_CFG(n)` registers at BAR1 + `0x10_8008`
(`+0x800` set / `+0xc00` clear aliases).

The downstream device tree places the RP1 peripherals (plus 64 KiB of shared
SRAM at `+0x40_0000`) at PCI address 0, i.e. CPU address `0x1f_0000_0000`
through PCIe2's 32-bit window. Bare-metal software relies on the firmware
leaving that configuration in place (`pciex4_reset=0` in `config.txt`), so
UART0 appears at `0x1f_0003_0000` (**unverified** on hardware).

## Boot flow

On hardware, the VideoCore firmware in the SPI EEPROM reads `config.txt`,
loads the device tree (applying overlays and fix-ups such as
`/memory`, `/chosen`, `/system/linux,revision`, the CMA size), the kernel
(`kernel_2712.img` by default) and TF-A BL31, which sits in the reserved
`atf@0` region (`0x0`–`0x80000`). The Arm cores start in BL31 at EL3; BL31
enters the kernel at EL2 with `x0` holding the device-tree address and
serves PSCI (`CPU_ON`, `SYSTEM_OFF`, `SYSTEM_RESET`) over SMC.

The `raspi5b` machine reproduces that contract (see
[raspi5b.rst](../../overlay/docs/system/arm/raspi5b.rst)), loading the
kernel and device tree where the firmware puts them; `config.txt`, the
files it names and the overlays it applies are `scripts/rpi5-boot`'s
(WS3 in the plan).

## Board revision

"New-style" code: `STYLE=1`, `MEMORY_SIZE=log2(size / 256 MiB)`,
`MANUFACTURER=0` (Sony UK), `PROCESSOR=4` (BCM2712), `TYPE=0x17` (5 Model B),
`REVISION`. For example 4 GiB revision 1.0 is `0xc04170`.
